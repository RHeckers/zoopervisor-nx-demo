# Zoopervisor

A reference **Nx + Angular** workspace for a talk on monorepo boundaries. It is
a teaching artifact: standalone components, signals, `inject()`, `@ngrx/signals`
stores, fake in-memory data, and **module boundaries that are computed, not
hand-maintained**.

---

## 1. The two root folders

```
apps/                    deployables — may depend on any domain + shared, nothing else
├── visitor/             web, public-facing (platform:desktop)
│   ├── shell/           THE app: src/ + public/ + bootstrap + routing  (type:app)
│   ├── features/        animal-list, enclosure-map                     (type:feature)
│   ├── slices/          app-level self-wiring block                    (type:slice)
│   ├── data-access/     cross-feature UI state                         (type:data-access)
│   ├── ui/              app-specific dumb components                   (type:ui)
│   └── e2e/             Playwright                                     (type:e2e)
├── keeper-mobile/       Capacitor-style (platform:mobile) — animal-detail feature
└── ticket-kiosk/        kiosk (platform:desktop) — buy-tickets feature

libs/                    domain code — a domain may depend on itself + shared, nothing else
├── animals/             data-access · slices · ui · utils · types
├── enclosures/          data-access · ui · types
├── feeding/             data-access · types
├── tickets/             data-access · ui · types   (PaymentProvider abstract DI token)
└── shared/              data-access · ui (+ mobile / desktop) · utils · types

tools/                   workspace tooling
├── nx-preset-zoo/       the local generator plugin (@zoo/nx-preset-zoo)
├── collect-tags.mjs     recursive project.json tag collector
├── affected-e2e.mjs     run only the e2e specs for affected libs
├── show-bundle-retention.mjs   the tree-shaking demo (§5)
└── verify.mjs           scripts the acceptance checks
```

Each leaf folder is one Nx project. `libs/<domain>/` and `apps/<app>/` are
grouping folders — no `project.json` there. Libraries are **non-buildable**: no
`package.json` per lib, wired only through `tsconfig.base.json` path aliases
(`@zoo/...`). Everything under `apps/<app>` lives beside the `shell/` project,
which is the one buildable app (its `src/` + `public/` live under `shell/`).

## 2. Tag scheme

Four axes. Every project carries `type:`. Library code carries `domain:` **or**
`app:`, never both. `platform:` is sparse.

| Axis | Values |
|---|---|
| `type:` (every project) | `app`, `feature`, `slice`, `ui`, `data-access`, `util`, `types`, `e2e` |
| `domain:` (libs) | `animals`, `enclosures`, `feeding`, `tickets`, `shared` |
| `app:` (everything under apps/) | `visitor`, `keeper-mobile`, `ticket-kiosk` |
| `platform:` (sparse) | `mobile` (keeper-mobile, shared/ui/mobile), `desktop` (visitor, ticket-kiosk, shared/ui/desktop) |

The boundary rules in `eslint.config.mjs` are **computed at load time** from
these tags (see `tools/collect-tags.mjs`): the type rules are static, but the
per-domain and per-app rules are generated by walking every `project.json`, so
adding a domain or app never edits an existing rule.

Layer direction (type rules): `app`/`feature` → anything downward; `slice` →
`ui`/`data-access`/`util`/`types`; `ui` and `data-access` are **peers** (neither
may reach the other); `util` → `util`/`types`; `types` → `types`.

## 3. Generate something

Every generator writes the correct tags into the new `project.json` — that is
the whole point of them.

```bash
# a whole domain (data-access, ui, utils, types; add --slices for a slices lib)
nx g @zoo/nx-preset-zoo:domain reptiles --slices

# one lib inside an existing domain (fails loudly if the domain doesn't exist)
nx g @zoo/nx-preset-zoo:domain-lib reptiles data-access

# a shared lib (optionally platform-scoped; ui only)
nx g @zoo/nx-preset-zoo:shared-lib ui --platform=mobile

# an app (src/ + public/ + bootstrap under shell/, plus an e2e sibling)
nx g @zoo/nx-preset-zoo:app signage --platform=desktop

# a lib inside an app (feature | slice | data-access | ui)
nx g @zoo/nx-preset-zoo:app-lib visitor ui

# an app feature, with its facade file scaffolded
nx g @zoo/nx-preset-zoo:feature visitor gift-shop
```

## 4. Try to break it

These imports **must** fail `nx lint`. `node tools/verify.mjs` (`npm run
verify`) scripts them, plus a check that every `project.json` has a `type:` tag.

| Add this import | Rejected by |
|---|---|
| `libs/animals/ui` → `@zoo/tickets/data-access` | domain rule |
| `libs/animals/ui` → `@zoo/animals/data-access` | type rule (ui ↛ data-access) |
| `libs/shared/ui/desktop` → `@zoo/shared/ui/mobile` | platform rule |
| any `platform:desktop` lib → `@capacitor/*` | banned external import |

Everything that *should* pass does: any app feature → any domain
`data-access`/`ui`/`slices`/`types`; any domain → `libs/shared/*`;
`libs/animals/slices` → `libs/animals/data-access`. `nx graph` shows a strictly
downward flow: apps → features → domains → shared.

```bash
nx run-many -t lint test build   # green on a clean checkout
npm run verify                   # acceptance checks
```

## 5. The deliberate tree-shaking violation

`libs/shared/utils/src/lib/zone-labels.util.ts` computes `ZONE_LABELS =
ZONES.map(...)` at **module-evaluation time**, so esbuild can't prove the module
is side-effect free and keeps it in any bundle that reaches the barrel — even
though nothing imports `ZONE_LABELS`. The fix lives next door in
`zone-labels.fixed.util.ts` (the map moved inside a function). Both are exported
from the barrel, and no `"sideEffects": false` is set anywhere.

```bash
npm run show-retention   # builds visitor twice; watch "reptile-house" appear then vanish
```
